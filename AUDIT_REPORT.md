**Stack:** Python 3.12, `python-telegram-bot 21.x`, Tornado 6.5, Supabase (PostgreSQL), Telegram Mini App (HTML/CSS/JS)

## 1. Critical Severity Issues

### ISSUE-CRIT-01: Client-Controlled Identity & Hardcoded User ID Fallback in WebApp
- **File:** `templates/webapp.html`, `webapp.py`
- **Line / Function:** `templates/webapp.html:2579`, `ApiDriveHandler.get()`, and all private API endpoints in `webapp.py`
- **Impact:** Complete authentication bypass. Any unauthenticated visitor on the internet can read, create, modify, star, or delete files of any user.
- **Attack Scenario:** An attacker visits `https://<domain>/api/drive?user_id=123456789` or opens `/webapp` with `?user_id=123456789`. The frontend and backend trust the user ID blindly. If no ID is supplied, it falls back to hardcoded ID `1166479771`.
- **Root Cause:** Identity is sourced from `tg?.initDataUnsafe?.user?.id`, `urlParams.get('user_id')`, or hardcoded `1166479771`. No server-side cryptographic validation of Telegram `initData` is performed.
- **Recommended Fix:** Implement centralized server-side validation of `initData` using the official HMAC-SHA256 algorithm with `BOT_TOKEN`. Reject all requests lacking valid `initData` (or valid server session token). Remove client-supplied `user_id` from request parameters.
- **Status:** Open (Fix scheduled in Phase 2)

---

### ISSUE-CRIT-02: Account Takeover via Unauthenticated Account Recovery
- **File:** `handlers/menu.py`, `handlers/settings.py`, `database.py`
- **Line / Function:** `handlers/menu.py:350-396` (`_process_recovery_key`), `handlers/menu.py:478-495` (`callback_recovery_link`), `handlers/settings.py:274-322`, `database.py:550-595` (`find_recoverable_account`, `transfer_user_data`)
- **Impact:** Immediate, total account hijacking. Any user can steal all folders and files belonging to any other user.
- **Attack Scenario:** Attacker sends text `DS-<victim_telegram_id>`, `<victim_telegram_id>`, or `@victim_username` to the bot, or triggers callback `rec:link:<victim_id>`. The bot calls `transfer_user_data(victim_id, attacker_id)`, transferring 100% of the victim's folders and files to the attacker with zero authentication or authorization from the victim.
- **Root Cause:** Recovery key is predictable (`DS-{user.id}`), username matching is considered proof of ownership, and callback accepts arbitrary target user IDs.
- **Recommended Fix:** Completely disable automatic username matching. Redesign recovery to require an explicit, cryptographically random, one-time, expiring, hashed recovery code generated by the authenticated owner account before transfer can occur.
- **Status:** Open (Fix scheduled in Phase 2 & 3)

---

### ISSUE-CRIT-03: Systemic IDOR & Missing Object Ownership Verification Across Private Endpoints
- **File:** `webapp.py`, `database.py`
- **Line / Function:** `ApiRenameHandler`, `ApiBatchMoveHandler`, `ApiBatchDeleteHandler`, `ApiStarHandler`, `ApiSendToChatHandler`, `ApiBatchSendToChatHandler`, `ApiDownloadHandler`, `ApiThumbnailHandler`, `ApiFileContentHandler`, `ApiTrashHandler`, `ApiRestoreHandler`, `ApiEmptyTrashHandler`, `ApiDuplicatesHandler`, `ApiCleanDuplicatesHandler`
- **Impact:** Cross-user data theft, data tampering, file deletion, and arbitrary Telegram message spamming.
- **Attack Scenario:** Attacker sends `POST /api/rename` with `{"id": 42, "new_name": "hacked"}`. The file is renamed regardless of who owns it. Attacker sends `GET /api/download?file_id=42` to retrieve any user's private file. Attacker sends `POST /api/send_to_chat` with `{"file_id": 42, "user_id": <victim_chat>}` to spam victims with arbitrary files.
- **Root Cause:** Database operations query by primary key only (`eq("id", file_id)`), without `eq("user_id", authenticated_user_id)` or ownership verification.
- **Recommended Fix:** Enforce ownership verification at the database query layer (`WHERE id = :id AND user_id = :authenticated_user_id`) and via centralized `require_file_owner(file_id, user_id)` / `require_folder_owner(folder_id, user_id)` helper guards.
- **Status:** Open (Fix scheduled in Phase 3)

---

### ISSUE-CRIT-04: IDOR in Telegram Bot Callback Queries
- **File:** `handlers/files.py`, `handlers/folders.py`, `handlers/settings.py`
- **Line / Function:** `preview_file` (`fi:`), `download_file` (`fdl:`), `delete_file_prompt` (`fx:`), `confirm_delete_file` (`fxc:`), `move_to_folder` (`fmt:`), `batch_download_folder` (`dlall:`), `download_folder_zip` (`dlzip:`), `open_folder` (`f:`), `delete_folder_prompt` (`dx:`), `confirm_delete_folder` (`dxc:`), `trash_restore` (`tr:`), `trash_permanent_delete` (`tp:`), `smart_folder_apply` (`smf_ok:`), `smart_apply_rename` (`smr_ok:`), `public_download_file` (`pdl:`)
- **Impact:** Any Telegram user can inspect, download, zip, move, trash, restore, or permanently destroy any other user's files and folders by crafting inline callback query data.
- **Attack Scenario:** Attacker sends callback query with data `fxc:105` or `tp:105` or `dlzip:12`. The handler invokes `db.trash_file(105)` or `db.permanent_delete(105)` or zips folder 12 without checking if the file/folder belongs to `query.from_user.id`.
- **Root Cause:** Callbacks unpack object IDs from callback strings and execute database mutations without checking `object.user_id == user_id`.
- **Recommended Fix:** Add ownership checks to every Telegram callback query handler before taking action.
- **Status:** Open (Fix scheduled in Phase 3)

### ISSUE-CRIT-05: Public File Sharing Security Bypass (Expiry, PIN, Limit & Direct Download)
- **File:** `webapp.py`, `database.py`, `utils.py`, `handlers/files.py`
- **Line / Function:** `PublicFileSharePageHandler.get()`, `ApiShareFileInfoHandler.get()`, `public_download_file()`, `utils.py:parse_share_token`, `database.py:get_file_by_share_token`
- **Impact:** Unrestricted access to protected files; bypass of PIN, expiration timestamps, and one-time download burning.
- **Attack Scenario:** 
  1. File has PIN and 24h expiration. Attacker requests `GET /s/{token}?download=1`. Lines 116-128 in `webapp.py` fetch the file and redirect to Telegram CDN immediately without checking PIN or expiration.
  2. `ApiShareFileInfoHandler` includes `preview_url` (direct Telegram CDN URL) in JSON response for any shared file, bypassing download limits and PIN gates.
  3. `public_download_file` in `handlers/files.py` (`pdl:{file_id}`) retrieves file by ID directly without verifying share token validity or PIN.
  4. Token lookup uses prefix matching `ilike("share_token", f"{token}%")` which allows token ambiguity and enumeration.
  5. PIN is stored as plaintext in the share token string `|pin:...|` and compared with simple equality.
  6. Download count increment is non-atomic and prone to race conditions for one-time links.
- **Root Cause:** Lack of centralized public share policy validation; direct CDN redirect without policy checks; plaintext PIN storage.
- **Recommended Fix:** Implement unified `validate_public_share(token, pin=None)` service function. Verify share existence, expiration, revocation, PIN (via salted hash + constant-time comparison), and download limit atomically. Ensure direct download and preview endpoints strictly enforce this policy.
- **Status:** Open (Fix scheduled in Phase 4)

## 2. High Severity Issues

### ISSUE-HIGH-01: Denial of Service via Unrestricted WebApp and Dropzone Multipart Uploads
- **File:** `webapp.py`
- **Line / Function:** `ApiUploadHandler.post()`, `ApiDropzoneUploadHandler.post()`
- **Impact:** Memory exhaustion (OOM), server crash, process termination on Render free tier (512MB RAM).
- **Attack Scenario:** Attacker uploads a 200MB file or 50 files simultaneously to `/api/dropzone/upload` or `/api/upload`. Tornado buffers the entire multipart payload in memory (`self.request.files`), exhausting container memory.
- **Root Cause:** No file size limits, no batch file count limits, and no total request size limits configured.
- **Recommended Fix:** Introduce configurable environment limits (`MAX_UPLOAD_FILE_SIZE_MB`, `MAX_UPLOAD_BATCH_FILES`, `MAX_UPLOAD_BATCH_MB`). Validate content length header and reject oversized payloads before buffering.
- **Status:** Open (Fix scheduled in Phase 5)

---

### ISSUE-HIGH-02: Missing Filename & User Input Sanitization
- **File:** `webapp.py`, `handlers/files.py`
- **Line / Function:** `ApiUploadHandler`, `ApiDropzoneUploadHandler`, `extract_file_info`
- **Impact:** Path traversal risks, control character injection, UI formatting corruption, excessively long filenames.
- **Attack Scenario:** Attacker sends files with names containing `../../`, null bytes, control characters, or 10,000 characters.
- **Root Cause:** Filename from `fileinfo["filename"]` is saved directly to the database without sanitization or length limits.
- **Recommended Fix:** Implement `sanitize_filename()` to strip path separators, control characters, null bytes, enforce UTF-8 normalization, and truncate to maximum 255 characters while preserving extensions safely.
- **Status:** Open (Fix scheduled in Phase 5)

---

### ISSUE-HIGH-03: Cross-Site Scripting (XSS) in Web Templates & Bot HTML Messages
- **File:** `templates/share_file.html`, `templates/webapp.html`, `handlers/inline.py`, `webapp.py`
- **Line / Function:** `templates/share_file.html:444`, `templates/share_file.html:486`, `templates/webapp.html:2899,2941`, `handlers/inline.py:88`, `webapp.py:387`
- **Impact:** Stored XSS in web browser; Telegram HTML parser crashes or message spoofing in chat.
- **Attack Scenario:** 
  1. In `share_file.html`: `previewArea.innerHTML = '<img class="preview-media-img" src="${previewUrl}" alt="${f.name}" onerror="renderDocFallback()">'`. A filename containing `"><script>alert(1)</script>` or `x" onerror="evil()"` executes arbitrary JavaScript.
  2. In `templates/webapp.html`: `onerror="... getFileIconSvg('${f.file_type}')"` evaluates raw file_type in JavaScript context.
  3. In Telegram bot handlers: user filenames are formatted directly into `parse_mode="HTML"` captions like `<b>{f['file_name']}</b>` without `html.escape()`. Malicious filenames break formatting or inject tags.
- **Root Cause:** Unescaped variables interpolated into HTML strings and `innerHTML` assignments.
- **Recommended Fix:** Apply strict HTML escaping (`html.escape` in Python, `escapeHtml` in JS) to all user-controlled variables. Avoid inline event handlers with dynamic string interpolation.
- **Status:** Open (Fix scheduled in Phase 5 & 7)

---

### ISSUE-HIGH-04: Cross-User Folder Placement & Nested Folder Tree Inconsistency
- **File:** `database.py`, `webapp.py`, `handlers/files.py`, `handlers/folders.py`
- **Line / Function:** `move_file`, `ApiBatchMoveHandler`, `create_folder`, `ApiCreateFolderHandler`
- **Impact:** User A can move their files into User B's folder, or set User B's folder as parent of their folder, causing cross-tenant data leakage or orphan structures.
- **Attack Scenario:** Attacker calls `/api/batch_move` with their own `file_ids` and a target `target_folder_id` belonging to another user. The system moves the files into the victim's folder hierarchy.
- **Root Cause:** Folder move and folder creation do not verify that `target_folder.user_id == authenticated_user_id` or that `parent_folder.user_id == authenticated_user_id`. Also, circular hierarchy checks are absent.
- **Recommended Fix:** Enforce `require_folder_owner` on destination folders and parent folders. Prevent moving a folder into itself or its descendants.
- **Status:** Open (Fix scheduled in Phase 3 & 6)

---

### ISSUE-HIGH-05: Verbose Error Disclosure & Stack Information Leakage
- **File:** `webapp.py`
- **Line / Function:** All `try...except` blocks in `webapp.py` returning `{"error": str(e)}`
- **Impact:** Leaks database schema, table names, SQL errors, connection strings, filesystem paths, and internal library details to clients.
- **Attack Scenario:** Attacker sends malformed input or triggers database constraint violation. The API responds with detailed Python traceback or database error message.
- **Root Cause:** Directly returning `str(e)` in JSON error responses.
- **Recommended Fix:** Return generic, sanitized error messages and standard HTTP error codes (`400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `500 Internal Server Error`). Log full stack traces server-side with structured correlation IDs.
- **Status:** Open (Fix scheduled in Phase 5)

---

### ISSUE-HIGH-06: Overly Permissive CORS on Private API Endpoints
- **File:** `webapp.py:31` (`BaseApiHandler.set_default_headers`)
- **Line / Function:** `self.set_header("Access-Control-Allow-Origin", "*")`
- **Impact:** Malicious external websites can make cross-origin requests to private API endpoints.
- **Attack Scenario:** A malicious site visited by a user initiates requests to `/api/drive` or state-changing APIs.
- **Root Cause:** Wildcard `*` used unconditionally for all endpoints.
- **Recommended Fix:** Restrict `Access-Control-Allow-Origin` to configured allowed origins (`ALLOWED_ORIGINS` / `WEBAPP_URL`) for private endpoints, while allowing public sharing endpoints where needed.
- **Status:** Open (Fix scheduled in Phase 8)

## 3. Medium Severity Issues

### ISSUE-MED-01: Blocking I/O in Async Tornado Handlers
- **File:** `webapp.py:750` (`ApiFileContentHandler.get()`)
- **Impact:** Event loop blocking; delays all concurrent requests and webhooks while downloading text preview.
- **Root Cause:** `urllib.request.urlopen(req)` is synchronous and executed directly on the Tornado event loop.
- **Recommended Fix:** Use Tornado's `AsyncHTTPClient()` or `asyncio.get_running_loop().run_in_executor()` with timeout.
- **Status:** Open (Fix scheduled in Phase 8)

---

### ISSUE-MED-02: Missing Graceful Cancellation in Background Keep-Alive Worker
- **File:** `bot.py:17-41` (`keep_alive_worker`)
- **Impact:** Unhandled task cancellation warnings or persistent hanging threads during shutdown / test execution.
- **Root Cause:** `while True:` loop without cancellation handling or tracking of task handle for shutdown.
- **Recommended Fix:** Track task reference, listen for `asyncio.CancelledError`, and cleanly terminate on application stop.
- **Status:** Open (Fix scheduled in Phase 8)

---

### ISSUE-MED-03: Hardcoded Deployment URLs in Source Code
- **File:** `config.py:12`, `webapp.py:925,967`
- **Impact:** Configuration inflexibility, unexpected behavior when deployed to custom domains.
- **Root Cause:** Hardcoded fallback string `"https://telegram-drive-bot-0upd.onrender.com"`.
- **Recommended Fix:** Introduce `PUBLIC_BASE_URL` config option; derive canonical base URLs cleanly without hardcoded domain literals.
- **Status:** Open (Fix scheduled in Phase 8)

---

### ISSUE-MED-04: Non-Atomic One-Time Link Invalidation
- **File:** `database.py:377-390` (`record_file_share_download`), `utils.py:encode_share_token`
- **Impact:** Race condition allows multiple simultaneous downloads for links configured with a download limit of 1.
- **Root Cause:** Download count is retrieved, incremented in Python, and written back without atomic locking or database-level concurrency control.
- **Recommended Fix:** Use atomic conditional update or SQL function ensuring only one concurrent request succeeds when `limit <= count`.
- **Status:** Open (Fix scheduled in Phase 4)

---

### ISSUE-MED-05: Missing Standard HTTP Security Headers
- **File:** `webapp.py` (`BaseApiHandler`, `WebAppPageHandler`, `PublicFileSharePageHandler`, `DropzonePageHandler`)
- **Impact:** Exposure to clickjacking, MIME-sniffing, and referrer leakage.
- **Root Cause:** No security headers (`X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, custom CSP suitable for Telegram WebApp) configured.
- **Recommended Fix:** Add standard security headers in base handler and page handlers without breaking Telegram WebApp iframe embedding.
- **Status:** Open (Fix scheduled in Phase 8)

## 4. Low & Informational Issues

### ISSUE-LOW-01: In-Memory Thumbnail Cache Unbounded per-Item Size
- **File:** `webapp.py:262` (`_THUMB_CACHE`)
- **Impact:** Memory spike if a large file thumbnail is loaded.
- **Recommended Fix:** Limit maximum binary size stored per cached thumbnail (e.g. 500KB max per entry).
- **Status:** Open (Fix scheduled in Phase 8)

### ISSUE-LOW-02: Missing Input Validation on Integer Parameters
- **File:** `webapp.py`
- **Impact:** Negative IDs or absurdly large numbers cause unexpected behavior or database errors.
- **Recommended Fix:** Validate IDs as positive 64-bit integers.
- **Status:** Open (Fix scheduled in Phase 5)

### ISSUE-LOW-03: Duplicate Route Definition in WebApp
- **File:** `webapp.py:1159-1191` and `webapp.py:1219-1250`
- **Impact:** Maintenance hazard where route updates are applied to one list but missed in the other.
- **Recommended Fix:** Consolidate routes into a single shared function/list.
- **Status:** Open (Fix scheduled in Phase 8)

### ISSUE-INFO-01: Supabase RLS Disabled Notice
- **File:** `setup.sql:45-47`
- **Impact:** When application uses service-role key on the backend, backend is the security perimeter. If Supabase key is leaked, direct access is possible.
- **Recommended Fix:** Ensure `SUPABASE_KEY` is strictly server-side and never exposed to client or logs.
- **Status:** Open (Audit verified in Phase 1)

### ISSUE-INFO-02: Missing `.env.example`
- **File:** Repository root
- **Impact:** Difficult onboarding and risk of accidental secret check-in.
- **Recommended Fix:** Create `.env.example` containing all required environment variables with blank/sample values.
- **Status:** Open (Fix scheduled in Phase 11)
